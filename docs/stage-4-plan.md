# Этап 4. Аномалии по истории метрик

Статус: проект плана от 31.10.2026, ожидает согласования. Ветка: `feature/anomaly-detection`.

## Цель

Научить ядро сравнивать числовую метрику текущей партии с историей без ручного задания
нормального числа строк или средней цены. Метод: двусторонняя z-оценка по скользящему окну.
Соответствие варианту OnlineNormal из Schelter 2018 требуется сверить с первоисточником
до реализации; скользящее окно само по себе не доказывает идентичность методов.

## Предлагаемое устройство

- Новый тип `anomaly`, параметры: метрика (`row_count`, `null_ratio`, `mean`), столбец при
  необходимости, область проверки, окно (30), порог z (3), минимальная история (30).
- Чистый детектор в `dq_monitor/anomalies/`: принимает текущее число и предыдущие числа,
  возвращает решение и вычисленные границы. Не знает про SQL, ORM и полигон.
- SQL измерения строится теми же шаблонами и коннектором; значения параметризуются.
- История берётся из `check_result.observed_value` для той же проверки, текущая точка
  исключается. Среднее и стандартное отклонение считаются по предыдущему окну.
- `observed_value` хранит исходную метрику, а не z; границы нормы сохраняются в
  `expected_low/high`, z и объём истории показываются в сообщении.
- Прогон использует существующие результаты и жизненный цикл инцидентов.
- Alembic: миграция CHECK для восьмого типа проверки. При необходимости — отдельное
  структурированное поле диагностики, решение после вычитки существующей модели.

## Семантика, которую нужно согласовать

1. Интеграция: отдельный тип `anomaly` (рекомендация) или дополнительный режим существующих
   проверок. Отдельный тип позволяет независимо сравнить правила, аномалии и комбинацию.
2. Метрики: `row_count`, `null_ratio`, `mean` сразу (рекомендация) или сначала только объём.
   Средняя цена нужна для дефекта «цены умножены на 10».
3. История: все прошлые конечные числовые значения, включая fail (рекомендация), или только pass.
   Первый вариант не отбирает историю по собственному решению детектора, но длительная порча
   постепенно сдвинет норму. Это ограничение описывается в записке.
4. Повторные прогоны одного дня: одна последняя пригодная точка на логический день для batch
   (рекомендация). Берутся только дни строго раньше текущего; будущие точки исключаются.
   Для table-области отдельно определить единицу истории: логический день или прогон.
5. Разогрев: отдельный статус `skip` (рекомендация, с миграцией CHECK и обновлением отчётов)
   или pass с сообщением. `skip` явно означает, что статистического решения ещё нет,
   не открывает и не закрывает инцидент. Прогон с пропусками должен показывать их отдельно.
6. Нулевая дисперсия: равное среднему значение проходит; любое отличающееся считается
   аномалией (рекомендация), либо вводится дополнительный абсолютный допуск.
7. Пустая партия: объём равен 0 и оценивается; среднее и доля NULL без строк дают skip.
   Ошибки запроса дают error. Ни skip, ни error не включаются в числовую историю.
8. После изменения параметров: отделить историю новой конфигурации от старой
   (рекомендация: fingerprint параметров в результате + миграция), либо вручную создавать
   новую проверку. Нельзя смешивать среднюю цену и объём при редактировании одной записи.
9. Дисперсия: выборочное стандартное отклонение, порог строго `abs(z) > threshold`, окно 30;
   окна 7/14/30 задаются параметрами. Настройки фиксируются до итогового эксперимента.

## Порядок работы

1. Сверить формулы и терминологию с первоисточником, утвердить семантику выше.
2. Написать чистый детектор, проверить на вручную рассчитанных рядах.
3. Добавить измерение метрик и выборку истории без текущих/будущих точек.
4. Обновить модели и миграции, реестр, runner, YAML-валидацию, отчёты и CLI для skip.
5. Добавить отдельный `checks/tpch-anomalies.yaml`, не менять пороги набора правил этапа 3.
6. Запустить чистые партии, затем контролируемые уменьшение объёма и сдвиг средней цены.
7. Записать принятые решения начиная с Р-29, обновить ERD, README и известные ограничения.
8. Подготовить страницу разбора кода для телефона; коммит и мерж после просмотра Тохой.

## Приёмка

- Разогрев не создаёт ложного успешного результата и не закрывает открытый инцидент.
- Текущая/будущая точка, error и пустые числовые значения не попадают в историю.
- Повторные прогоны дня и смена параметров не искажают окно.
- Проверены точное равенство порогу, нулевая дисперсия, недостаток истории и часовые пояса.
- Новые дефекты обнаруживаются; серия fail и последующий pass корректно ведут инцидент.
- Upgrade/downgrade и alembic check работают; тесты этапов 0–3 проходят.
- На SF 1 измерены время прогона и частота тревог на чистых данных. Нулевая частота заранее
  не обещается: статистический порог допускает срабатывания.
- Итоговые precision/recall и сравнение методов остаются частью этапа 8.
