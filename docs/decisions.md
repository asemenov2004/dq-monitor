# Журнал технических решений

Формат записи: контекст, рассмотренные варианты, принятое решение, обоснование.

## Р-01. Размещение исходного кода

**Дата:** 09.10.2026
**Контекст:** исходный код должен быть доступен научному руководителю и комиссии.
**Варианты:** публичный репозиторий GitHub; приватный репозиторий с выдачей доступа.
**Решение:** публичный репозиторий GitHub, лицензия MIT.
**Обоснование:** доступ по ссылке без дополнительных действий; явная лицензия определяет условия использования кода.

## Р-02. Управление зависимостями

**Дата:** 09.10.2026
**Варианты:** pip + venv; uv; Poetry.
**Решение:** pip + venv, зависимости описаны в `pyproject.toml`, пакет ставится командой `pip install -e ".[dev]"`.
**Обоснование:** стандартные средства Python без дополнительных инструментов; `pyproject.toml` (PEP 621)
описывает и зависимости, и сам пакет, что потребуется для установки ядра в окружение Airflow.

## Р-03. Ветвление

**Дата:** 09.10.2026
**Решение:** ветка `main` всегда в рабочем состоянии; каждый этап разрабатывается в ветке
`feature/<суть>` и вливается в `main` после проверки.
**Обоснование:** в истории репозитория видно, какие изменения относятся к какому этапу; незавершённый этап не ломает рабочую версию.

## Р-04. Структура пакета

**Дата:** 09.10.2026
**Варианты:** src-layout (`src/dq_monitor/`); пакет в корне репозитория.
**Решение:** src-layout.
**Обоснование:** тесты выполняются против установленного пакета, а не против файлов в текущей папке,
поэтому ошибки упаковки обнаруживаются сразу.

## Р-05. Размещение баз данных

**Дата:** 09.10.2026
**Варианты:** один сервер PostgreSQL с двумя базами; два отдельных контейнера.
**Решение:** один контейнер PostgreSQL 17 с базами `warehouse` (хранилище) и `meta` (метаданные системы).
**Обоснование:** меньше потребление памяти на рабочей машине. Код обращается к базам по разным адресам подключения,
поэтому перенос хранилища на отдельный сервер требует только изменения настроек.
Порт на хосте 5433, так как стандартный 5432 занят локальным PostgreSQL.

## Р-06. Конфигурация

**Дата:** 09.10.2026
**Варианты:** файл `.env` + pydantic-settings; YAML-файл.
**Решение:** `.env` + pydantic-settings; в репозитории хранится только шаблон `.env.example`.
**Обоснование:** тот же механизм используют Docker Compose и Airflow; секреты (пароли, токен бота) не попадают в репозиторий;
pydantic проверяет типы значений при запуске.

## Р-07. Контроль качества кода

**Дата:** 09.10.2026
**Решение:** pytest для тестов, ruff для статического анализа и форматирования.
**Обоснование:** ruff объединяет линтер и форматтер в одном инструменте и работает быстро.

# Известные ограничения

## О-01. Файл `.env` ищется относительно текущей папки

**Выявлено:** 09.10.2026, этап 0.
**Суть:** настройки читаются из `.env` в папке, из которой запущена программа. При запуске из другой папки файл не будет найден.
**Когда решать:** этап 6 (Airflow). В контейнере Airflow настройки передаются через переменные окружения, файл `.env` там не используется.

## О-02. Новый пул соединений при каждом обращении к базе

**Выявлено:** 09.10.2026, этап 0.
**Суть:** функции `warehouse_engine()` и `meta_engine()` при каждом вызове создают новый объект Engine со своим пулом соединений.
Для команды `ping` это несущественно, но при выполнении множества проверок за один прогон приводит к лишним подключениям.
**Когда решать:** этап 3 (ядро проверок): один Engine на процесс, кэшируется через `functools.lru_cache`.
