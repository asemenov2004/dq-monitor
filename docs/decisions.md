# Журнал технических решений

Формат записи: контекст, рассмотренные варианты, принятое решение, обоснование.
Журнал служит основой для раздела пояснительной записки об обосновании технических решений.

## Р-01. Размещение исходного кода

**Дата:** 09.10.2026
**Контекст:** исходный код должен быть доступен научному руководителю и комиссии.
**Варианты:** публичный репозиторий GitHub; приватный репозиторий с выдачей доступа.
**Решение:** публичный репозиторий GitHub, лицензия MIT.
**Обоснование:** доступ по ссылке без дополнительных действий; явная лицензия определяет условия использования кода.

## Р-02. Управление зависимостями

**Дата:** 09.10.2026
**Варианты:** pip + venv; uv; Poetry.
**Решение:** pip + venv, зависимости описаны в `pyproject.toml`, пакет ставится командой `pip install -e ".[dev]"`.
**Обоснование:** стандартные средства Python без дополнительных инструментов; `pyproject.toml` (PEP 621)
описывает и зависимости, и сам пакет, что потребуется для установки ядра в окружение Airflow.

## Р-03. Ветвление

**Дата:** 09.10.2026
**Решение:** ветка `main` всегда в рабочем состоянии; каждый этап разрабатывается в ветке
`feature/<суть>` и вливается в `main` после проверки.
**Обоснование:** в истории репозитория видно, какие изменения относятся к какому этапу; незавершённый этап не ломает рабочую версию.

## Р-04. Структура пакета

**Дата:** 09.10.2026
**Варианты:** src-layout (`src/dq_monitor/`); пакет в корне репозитория.
**Решение:** src-layout.
**Обоснование:** тесты выполняются против установленного пакета, а не против файлов в текущей папке,
поэтому ошибки упаковки обнаруживаются сразу.

## Р-05. Размещение баз данных

**Дата:** 09.10.2026
**Варианты:** один сервер PostgreSQL с двумя базами; два отдельных контейнера.
**Решение:** один контейнер PostgreSQL 17 с базами `warehouse` (хранилище) и `meta` (метаданные системы).
**Обоснование:** меньше потребление памяти на рабочей машине. Код обращается к базам по разным адресам подключения,
поэтому перенос хранилища на отдельный сервер требует только изменения настроек.
Порт на хосте 5433, так как стандартный 5432 занят локальным PostgreSQL.

## Р-06. Конфигурация

**Дата:** 09.10.2026
**Варианты:** файл `.env` + pydantic-settings; YAML-файл.
**Решение:** `.env` + pydantic-settings; в репозитории хранится только шаблон `.env.example`.
**Обоснование:** тот же механизм используют Docker Compose и Airflow; секреты (пароли, токен бота) не попадают в репозиторий;
pydantic проверяет типы значений при запуске.

## Р-07. Контроль качества кода

**Дата:** 09.10.2026
**Решение:** pytest для тестов, ruff для статического анализа и форматирования.
**Обоснование:** ruff объединяет линтер и форматтер в одном инструменте и работает быстро.

## Р-08. Генератор тестовых данных

**Дата:** 10.10.2026
**Варианты:** расширение `tpch` в DuckDB; оригинальная утилита dbgen; готовые CSV-файлы из открытых источников.
**Решение:** DuckDB (`CALL dbgen(sf = ...)`), запись в PostgreSQL через расширение `postgres` для DuckDB.
**Обоснование:** DuckDB содержит встроенную реализацию dbgen и генерирует данные, идентичные эталонным;
устанавливается как Python-пакет, не требует сборки под Windows. Генерация и выгрузка SF 1 занимают около 1 минуты.

## Р-09. Размещение кода полигона

**Дата:** 10.10.2026
**Варианты:** отдельный пакет `dq_stand` в том же репозитории; подпакет внутри `dq_monitor`; отдельный репозиторий.
**Решение:** отдельный пакет `src/dq_stand`, зависимость `duckdb` вынесена в группу `stand`.
**Обоснование:** физически разделены предмет работы (ядро `dq_monitor`) и вспомогательный экспериментальный стенд.
Ядро не зависит от стенда и устанавливается без DuckDB.

## Р-10. Схемы хранилища

**Дата:** 10.10.2026
**Решение:** в базе `warehouse` три схемы: `src` (полный слепок сгенерированных данных, источник партий),
`dwh` (контролируемое хранилище, факты догружаются по дням), `stand` (служебные таблицы полигона: модельные часы, журнал загрузок).
**Обоснование:** загрузка партии выполняется одним запросом `INSERT ... SELECT` внутри СУБД; инжектор дефектов
(этап 8) сможет вмешиваться в данные на этом шаге. Цена решения: данные хранятся дважды (около 1,5 ГБ для SF 1).

## Р-11. Ограничения целостности и индексы в dwh

**Дата:** 10.10.2026
**Варианты:** без первичных и внешних ключей; с ключами.
**Решение:** в `dwh` нет ни первичных, ни внешних ключей, ни ограничений NOT NULL, ни индексов.
**Обоснование:** в аналитических хранилищах ограничения целостности, как правило, не навязываются
(в ClickHouse они отсутствуют), именно поэтому требуется внешний контроль качества данных. С ключами внести
в данные дубли и ссылки на несуществующие записи для эксперимента было бы невозможно. Индексы не нужны
при текущем объёме (сотни тысяч строк после сотен партий); будут добавлены, если замеры покажут необходимость.

## Р-12. Сдвиг дат TPC-H

**Дата:** 10.10.2026
**Решение:** все даты (`o_orderdate`, `l_shipdate`, `l_commitdate`, `l_receiptdate`) сдвигаются на одинаковое
число дней так, чтобы данные начинались с даты из настройки `STAND_START_DATE` (по умолчанию 01.01.2025).
**Обоснование:** правдоподобные даты в графиках и примерах. Сдвиг выполняется в днях, а не в годах:
при сдвиге на годы 29 февраля переходит в 28-е, и два разных дня сливаются в одну партию.

## Р-13. Модельное время

**Дата:** 10.10.2026
**Контекст:** при загрузке сотен партий за минуты реальное время непригодно для проверки свежести данных.
**Варианты:** модельное «сейчас» = максимальное время загрузки в данных; отдельные модельные часы.
**Решение:** отдельные часы в таблице `stand.clock`. Цикл загрузки: часы сдвигаются на сутки,
затем загружается партия за предыдущий день (`batch_date` = D, `loaded_at` = D+1 02:00).
**Обоснование:** часы, вычисляемые по данным, останавливаются вместе с данными, и задержка загрузки
становится принципиально необнаружимой. Отдельные часы идут независимо от загрузок. Ядро проверок получает
текущее время как параметр и не зависит от того, модельное оно или реальное.

## Р-14. Описание схемы базы метаданных

**Дата:** 13.10.2026
**Варианты:** SQLAlchemy ORM (классы-модели); SQLAlchemy Core (таблицы без классов); SQL-скрипты.
**Решение:** SQLAlchemy ORM, модели в `dq_monitor/meta/models.py`.
**Обоснование:** одни и те же классы используются ядром проверок и веб-интерфейсом; схема описана в одном месте,
миграции генерируются из неё.

## Р-15. Миграции схемы

**Дата:** 13.10.2026
**Варианты:** Alembic; собственные пронумерованные SQL-файлы; создание схемы без миграций (`create_all`).
**Решение:** Alembic, миграции в `dq_monitor/meta/migrations` (ставятся вместе с пакетом).
**Обоснование:** стандартный инструмент для SQLAlchemy; миграция генерируется по разнице моделей и базы и
вычитывается вручную; изменения схемы версионируются и обратимы без потери накопленной истории проверок.
Ограничения именуются по единому соглашению, чтобы миграции могли ссылаться на них по имени.

## Р-16. Прогон и результат проверки

**Дата:** 13.10.2026
**Варианты:** одна сущность «запуск проверки»; прогон (`run`) и результат проверки (`check_result`) раздельно.
**Решение:** раздельно. Прогон хранит логическое время (`logical_now`), с которым выполнялись проверки,
и реальное время начала и окончания.
**Обоснование:** планировщик выполняет набор проверок за один заход; в эксперименте один цикл загрузки соответствует
одному прогону. Метрики эксперимента по циклам и накладные расходы на прогон получаются одним запросом.
Логическое время отделяет модельное время полигона от реального.

## Р-17. Инцидент

**Дата:** 13.10.2026
**Решение:** инцидент привязан к проверке и имеет жизненный цикл: открывается при первом неуспешном результате,
закрывается при первом успешном. Состояния `open` и `closed`; не больше одного открытого инцидента на проверку
(частичный уникальный индекс).
**Обоснование:** серия неуспешных прогонов одной проверки является одной проблемой; без этого оповещения
дублировались бы на каждом прогоне. Состояние «взято в работу» в MVP не требуется.

## Р-18. Ограничения целостности в базе метаданных

**Дата:** 13.10.2026
**Решение:** полный набор PK, FK, NOT NULL, UNIQUE и CHECK; перечисления хранятся как `varchar` с ограничением CHECK;
внешние ключи `ON DELETE RESTRICT`, проверка выводится из работы флагом `is_active`.
**Обоснование:** в отличие от контролируемого хранилища (Р-11), база метаданных принадлежит самой системе,
и запись в неё некорректных данных должна быть невозможна. CHECK вместо типов ENUM: их проще изменять миграциями.
RESTRICT защищает историю результатов от удаления.

## Р-19. Подключение к хранилищу в метаданных

**Дата:** 13.10.2026
**Решение:** таблица `connection` хранит адрес, имя базы и пользователя, а вместо пароля имя переменной окружения,
в которой он лежит.
**Обоснование:** секреты не попадают в базу метаданных и в её резервные копии. Тип СУБД (`db_type`) позволяет
добавить коннектор ClickHouse без изменения схемы.

## Р-20. Устройство ядра проверок

**Дата:** 18.10.2026
**Решение:** каждый тип проверки является подклассом абстрактного класса `Check` и задаёт три элемента:
модель параметров (pydantic), построение SQL-запроса (`build_query`) и оценку результата (`evaluate`).
Общий алгоритм выполнения (`run`: построить запрос, выполнить, оценить) определён в базовом классе
(шаблонный метод). Реестр сопоставляет имя типа с классом.
**Обоснование:** новый тип проверки добавляется одним классом без изменения прогона; неверные параметры
отклоняются до обращения к хранилищу; построение запроса и оценка тестируются раздельно и без СУБД.

## Р-21. Построение SQL-запросов

**Дата:** 18.10.2026
**Варианты:** шаблоны строк с экранированием имён средствами диалекта; выражения SQLAlchemy Core.
**Решение:** единые для всех СУБД шаблоны на стандартном подмножестве SQL (`COUNT`, `SUM(CASE ...)`, `GROUP BY`,
`LEFT JOIN`, `MAX`). Значения (даты, пороги, списки) передаются параметрами запроса и в его текст не попадают;
имена схем, таблиц и столбцов экранирует коннектор средствами диалекта СУБД; арифметика времени (возраст данных)
выполняется в Python, а не в SQL.
**Обоснование:** запрос, который строит проверка, читается как обычный SQL и может быть показан пользователю
(команда `checks sql`). Различия СУБД сведены к методам коннектора. Параметризация значений и экранирование имён
исключают SQL-инъекции через параметры проверок.

## Р-22. Область проверки: ожидаемая партия

**Дата:** 18.10.2026
**Варианты:** последняя загруженная партия; ожидаемая партия (за сутки до логического времени); вся таблица.
**Решение:** для таблиц со столбцом партии по умолчанию проверяется ожидаемая партия, параметр `scope: table`
переключает проверку на всю таблицу; справочники проверяются целиком. Проверка свежести всегда оценивает всю таблицу.
**Обоснование:** при проверке последней загруженной партии отсутствие новой партии осталось бы незамеченным:
проверки повторно оценили бы вчерашние данные. Ожидаемая партия при отсутствии данных даёт 0 строк, и это ловит
проверка объёма.

## Р-23. Безопасность выполнения проверок

**Дата:** 18.10.2026
**Решение:** коннектор устанавливает при подключении параметры сеанса `default_transaction_read_only=on` и
`statement_timeout` (по умолчанию 60 с, настройка `CHECK_STATEMENT_TIMEOUT_SEC`); транзакции проверок не фиксируются.
**Обоснование:** ограничения применяет сервер СУБД к каждой транзакции, поэтому их нельзя обойти текстом запроса
(в том числе в `custom_sql`): попытка изменить данные отклоняется, долгий запрос прерывается и не задерживает прогон.

## Р-24. Изоляция ошибок и статус error

**Дата:** 18.10.2026
**Решение:** исключение при выполнении одной проверки не прерывает прогон, а сохраняется как результат со статусом
`error` и понятным сообщением. Статус `error` не открывает и не закрывает инцидент. Результат каждой проверки
фиксируется в базе сразу после выполнения.
**Обоснование:** ошибка выполнения (синтаксис, недоступность, таймаут) не является сведением о качестве данных
и в эксперименте не должна засчитываться ни как обнаружение дефекта, ни как его устранение. Немедленная фиксация
сохраняет результаты при аварийном завершении прогона.

## Р-25. Время инцидентов

**Дата:** 18.10.2026
**Решение:** моменты открытия и закрытия инцидента берутся из логического времени прогона (`logical_now`).
**Обоснование:** в эксперименте задержка обнаружения измеряется в модельном времени; в эксплуатации логическое
время совпадает с реальным.

## Р-26. Набор проверок как файл

**Дата:** 18.10.2026
**Варианты:** YAML-файл в репозитории с загрузкой командой; ввод проверок командами консоли.
**Решение:** YAML (`checks/tpch.yaml`), команда `checks load`. Загрузка идемпотентна (добавляет новые, обновляет
изменившиеся, не трогает совпадающие); файл проверяется целиком, и при любой ошибке в базу не записывается ничего,
а пользователю выводятся все найденные ошибки сразу.
**Обоснование:** методика эксперимента требует фиксации набора проверок и порогов до его начала; файл под контролем
версий это подтверждает. Пороги набора выбраны по профилю данных SF 1 и прокомментированы в файле.

## Р-27. Семантика типов проверок

**Дата:** 18.10.2026
**Решение:** пустое значение (NULL) не считается нарушением диапазона и висячей ссылкой: за него отвечает `not_null`;
долевые проверки (`not_null`, `range`) на пустой партии дают `pass` без значения, пустоту ловит `row_count`;
уникальность считается через `GROUP BY ... HAVING COUNT(*) > 1` (переносимо, в отличие от `COUNT(DISTINCT)`
по нескольким столбцам); наблюдаемое значение `unique` и `referential` равно числу нарушающих строк.
**Обоснование:** каждый вид дефекта обнаруживается одной профильной проверкой, без дублирующих срабатываний;
это упрощает интерпретацию результатов эксперимента (матрица «тип дефекта × тип проверки»).

## Р-28. Связка полигона и ядра

**Дата:** 18.10.2026
**Решение:** команда полигона `dq_stand cycle` выполняет цикл «загрузить партию, прогнать проверки» и передаёт ядру
модельное время как логическое. Ядро о модельных часах не знает.
**Обоснование:** зависимость направлена от стенда к ядру; в эксплуатации логическое время ядру передаёт планировщик.

## Р-29. Детектор аномалий

**Дата:** 31.10.2026
**Варианты:** отдельный тип anomaly; дополнительный режим существующих правил.
**Решение:** отдельный тип с метриками row_count, null_ratio и mean; чистый детектор на Python.
**Обоснование:** правила и аномалии независимо включаются для сравнения в эксперименте,
формулы проверяются без СУБД. Среднее необходимо для обнаружения смещения цен.

## Р-30. Статистический метод

**Дата:** 31.10.2026
**Решение:** двусторонняя z-оценка по скользящему окну, выборочное стандартное отклонение n−1,
порог строго |z| > threshold (по умолчанию 3), окно 30. При нулевой дисперсии равное среднему
значение проходит, любое отличие считается аномалией; неопределённый z не сохраняется числом.
**Основание:** Schelter et al., 2018, раздел 3.4:
https://www.vldb.org/pvldb/vol11/p1781-schelter.pdf . OnlineNormal использует оценку среднего
и дисперсии с порогом стандартных отклонений. Наша конкретизация окна и делителя дисперсии
не объявляется точной копией реализации OnlineNormal.

## Р-31. История по дням UTC

**Дата:** 31.10.2026
**Варианты:** последние результаты прогонов; последняя попытка на каждый прошлый день UTC.
**Решение:** календарный интервал [текущий день − window; текущий день), последняя попытка
дня той же версии проверки. Текущий день и более поздние run_id исключаются.
**Обоснование:** повторные прогоны не увеличивают вес партии, а после длинного перерыва
детектор не обучается на устаревшей норме. Для table-области единица истории также день UTC.
Числовые PASS, FAIL и SKIP разогрева используются. ERROR и SKIP без метрики не используются;
если последняя попытка дня непригодна, более старая успешная попытка её не заменяет.

## Р-32. Разогрев и отсутствующие измерения

**Дата:** 31.10.2026
**Варианты:** pass с пояснением; отдельный статус skip.
**Решение:** skip с измеренным числом при разогреве, skip без числа при неопределённой
метрике. min_history по умолчанию равен window, допустимо от 2 до window.
**Обоснование:** недостаток оснований для оценки не выдаётся за успешную проверку данных.
Числовой skip разогрева накапливает историю. Пустая партия даёт row_count=0, но mean и
null_ratio не определены. skip не меняет инцидент; код выхода 0 при PASS/SKIP позволяет
выполнять автоматические циклы разогрева. Счётчик skip отдельно выводится в отчёте.

## Р-33. Версионирование истории

**Дата:** 31.10.2026
**Варианты:** новая проверка вручную при смене параметров; версия конфигурации в каждом результате.
**Решение:** SHA-256 нормализованных параметров, типа, датасета и источника в config_hash.
**Обоснование:** история средней цены не смешивается с историей объёма при редактировании
проверки. Описание и severity на измерение не влияют и не включаются в версию. История
старой версии сохраняется, при возврате конфигурации доступна в пределах окна.

## Р-34. Диагностика и эволюция схемы

**Дата:** 31.10.2026
**Решение:** observed_value хранит исходную метрику, expected_low/high — вычисленные границы,
JSONB details — среднее, s, z, число точек, параметры и причину skip. Миграция b2e4a6c8d010
добавляет поля, тип anomaly и статус skip без изменения старых результатов.
**Обоснование:** история пригодна для повторного анализа и графиков; диагностика не требует
разбора текстовых сообщений. Downgrade запрещён при наличии новых типов данных и не удаляет
их молча. Старые результаты без config_hash не служат историей новых anomaly-проверок.

## Р-35. Airflow перед оповещениями

**Дата:** 31.10.2026
**Решение:** этап 6 (расписание) выполняется после этапа 4. Этап 5 (Telegram) отложен
до обсуждения с научным руководителем, нумерация этапов сохраняется.
**Обоснование:** планирование зависит от готового ядра, но не от оповещений.

## Р-36. Развёртывание Airflow

**Дата:** 31.10.2026
**Варианты:** LocalExecutor; CeleryExecutor с Redis и workers; standalone в одном контейнере.
**Решение:** официальный apache/airflow:3.3.2, отдельные API, scheduler, dag-processor,
LocalExecutor с parallelism=1. Образ содержит установленный пакет dq-monitor и миграции.
**Обоснование:** для одного DAG не нужен распределённый исполнитель; отдельные компоненты
управляются Compose. Airflow не ставится в Windows-venv. Его зависимости закрепляются
constraints-файлом официального образа; pip check проверяет совместимость пакета.

## Р-37. Окружение и базы Airflow

**Дата:** 31.10.2026
**Решение:** отдельная БД airflow и роль airflow в существующем PostgreSQL, подготовка
идемпотентным init-сервисом, без пересоздания volume PostgreSQL. Логи и общие ключи
API/scheduler сохраняются в Docker volumes. Локальный UI с SimpleAuthManager на 127.0.0.1:8081.
**Обоснование:** история оркестратора отделена от метаданных приложения, память не тратится
на второй сервер СУБД. Ключи генерируются при инициализации и не попадают в git.
Основание: https://airflow.apache.org/docs/apache-airflow/3.3.2/howto/docker-compose/index.html
и https://airflow.apache.org/docs/apache-airflow/3.3.2/core-concepts/auth-manager/simple/index.html .
Конфигурация предназначена для локального дипломного стенда, не для публичного сервера.

## Р-38. Расписание в ядре

**Дата:** 31.10.2026
**Варианты:** отдельный DAG на проверку; один DAG с выбором проверок в ядре.
**Решение:** один DAG раз в минуту вызывает run_due_checks. Cron из пяти полей считается
в реальном UTC, NULL означает каждый тик. Новая проверка подхватывается на первом тике.
Пропущенные интервалы объединяются в один, backfill не выполняется.
**Обоснование:** бизнес-логика не зависит от Airflow; тот же запуск доступен командой run --due.
При ручном Trigger вызывается обычный run_checks, без изменения расписаний. Параметр
logical_now служит только для ручной демонстрации на модельном времени; scheduled-запуск
использует настоящее время. Ни DAG, ни scheduler не загружают данные в хранилище.

## Р-39. Учёт обработанного интервала

**Дата:** 31.10.2026
**Решение:** check_result.scheduled_for хранит реальную UTC-дату cron-интервала;
UNIQUE(check_id, scheduled_for) защищает от повторной записи. У ручных результатов NULL.
**Обоснование:** повторный тик или перезапуск процесса не выполняют обработанный интервал
заново. FAIL/ERROR также считаются попыткой, следующая идёт в новом интервале. При аварии
уже сохранённые результаты остаются, недостигнутые проверки могут быть выполнены снова.
Смена schedule не переигрывает интервалы раньше последнего scheduled_for. При downgrade
служебные интервалы удаляются, сами результаты сохраняются.

## Р-40. Конкуренция прогонов

**Дата:** 31.10.2026
**Варианты:** ограничение только в DAG; общая блокировка в PostgreSQL.
**Решение:** session-level advisory lock для всех прогонов, включая CLI и полигон. То же
соединение используется для ORM-метаданных, поэтому потеря lock-backend останавливает
дальнейшую запись. DAG дополнительно ограничен max_active_runs=1, catchup=False.
**Обоснование:** ограничение Airflow не защищает от ручного CLI. PostgreSQL сам освобождает
lock при завершении backend; блокировка переживает промежуточные коммиты результатов.
Занятый lock даёт понятную ошибку CLI и SKIPPED в Airflow. Применяется к одной базе meta.

## Р-41. Маршрутизация и статус задачи

**Дата:** 31.10.2026
**Решение:** DQ_CONNECTION_OVERRIDES задаёт host/port того же источника по имени подключения:
tpch_warehouse внутри Docker использует postgres:5432 вместо Windows localhost:5433.
**Обоснование:** один каталог источников работает с Windows и из контейнера без правки БД.
Метаданные источника и история конфигурации не меняются при смене сетевого маршрута.
Airflow получает полный текстовый отчёт; FAIL/ERROR делают задачу failed, PASS/SKIP дают
success. retries=0, потому что повтор задачи не исправляет дефект данных. Telegram не требуется.

**Альтернативы:** отдельный frontend React; Streamlit.
**Обоснование:** пользователь выбрал полноценные формы без отдельной сборки frontend.

## Р-45. Transactional outbox

**Дата:** 08.11.2026
**Решение:** открытие/закрытие инцидента и постановка сообщений в очередь фиксируются
одной транзакцией. Сеть вызывает отдельный worker под собственной advisory lock.
**Альтернативы:** отправлять прямо из runner; отдавать отправку только Airflow.
**Обоснование:** сбой SMTP/HTTP не должен терять событие или мешать сохранению проверки.
Повторный FAIL не создаёт новое событие; уникальность для новых каналов защищает
от повторной постановки. Старая история Telegram сохраняется. Попытка фиксируется
до сети, число попыток ограничено, задержка растёт. Закрытие ждёт доставленного
открытия своего канала; для старого инцидента без сообщения об открытии допускается
самостоятельная доставка закрытия. Гарантия at least once допускает дубль при crash
после принятия сообщения сервисом до commit статуса sent.

# Известные ограничения

Повторная проверка MVP 08.11.2026: демонстрационные команды возвращают собственным
правилам исходные параметры и активность, чтобы редактирование в UI не ломало
следующий показ. PostgreSQL получил restart: unless-stopped, как зависимые сервисы.
Веб-тесты используют уникальную временную БД на процесс. Проверка: 309 тестов,
повторные сценарии доставки и anomaly прошли.

## О-01. Файл `.env` ищется относительно текущей папки

**Выявлено:** 09.10.2026, этап 0.
**Суть:** настройки читаются из `.env` в папке, из которой запущена программа. При запуске из другой папки файл не будет найден.
**Когда решать:** этап 6 (Airflow). В контейнере Airflow настройки передаются через переменные окружения, файл `.env` там не используется.

## О-02. Новый пул соединений при каждом обращении к базе

**Выявлено:** 09.10.2026, этап 0. **Решено:** 18.10.2026, этап 3.
**Суть:** функции `warehouse_engine()` и `meta_engine()` при каждом вызове создают новый объект Engine.
**Решение:** прогон создаёт один коннектор (и один пул соединений) на каждое подключение к хранилищу и использует его
для всех проверок прогона, после прогона соединения закрываются. Функции из `db.py` вызываются один раз на команду.

## О-03. Время прогона растёт с объёмом таблиц

**Выявлено:** 18.10.2026, этап 3.
**Суть:** в `dwh` нет индексов (Р-11), поэтому проверки партии читают таблицу целиком. На SF 1 прогон 22 проверок
занимает 0,35 с при 33 загруженных партиях и 0,50 с при 203 (среднее 0,42 с, максимум 0,68 с за 170 прогонов).
**Когда решать:** этап 8, по результатам замеров накладных расходов; вариант решения: индекс по `batch_date`.

## О-04. Расписание проверок не учитывается

**Выявлено:** 18.10.2026, этап 3. **Решено:** 31.10.2026, этап 6.
**Решение:** run_due_checks и команда run --due учитывают cron, а ручной run выполняет
все активные проверки. Тот же выбор наступивших правил используется scheduled-запусками DAG.

## О-05. Одновременные прогоны

**Выявлено:** 18.10.2026, этап 3. **Решено:** 31.10.2026, этап 6.
**Решение:** общая PostgreSQL advisory lock для CLI, полигона и Airflow, с записью результатов
через удерживающее блокировку соединение; дополнительно max_active_runs=1 в DAG.

## О-06. Статистические тревоги и дрейф

**Выявлено:** 31.10.2026, этап 4.
**Суть:** z-оценка не моделирует сезонность и тренды, а длительная порча смещает норму,
поскольку FAIL входят в историю. При постоянной истории любое отклонение считается аномалией.
**Наблюдение:** на SF 1 после 30 дней разогрева за 30 чистых дней получена одна тревога
lineitem_volume_anomaly на 40-й партии (2194 строки). Порог 3 после наблюдения не изменялся.
**Когда решать:** этап 8: оценить precision/recall и влияние размера окна на заранее размеченном плане.

## О-07. Повторный разогрев после пропусков

**Выявлено:** 31.10.2026, этап 4.
**Суть:** при недостатке пригодных дней внутри календарного окна возвращается skip.
По умолчанию нужны все window точек, поэтому день без измерения временно мешает оценке.
**Вариант настройки:** заранее задать min_history меньше window (не менее 2),
явно принимая решение по меньшему числу наблюдений. Для итогового эксперимента настройку
фиксировать до прогона, а не менять в ответ на результаты.
