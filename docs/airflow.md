# Airflow: запуск, демонстрация и разбор этапа 6

Telegram (этап 5) отложен до обсуждения с научным руководителем. Для запуска проверок
оповещения не требуются. Номера этапов сохраняются.

## Что появилось

Один DAG `dq_monitor_checks` раз в минуту вызывает ядро. Ядро перечитывает активные
проверки из meta, выбирает наступившие расписания, выполняет проверки и сохраняет
результаты и инциденты. Создание новой проверки в meta не требует перезапуска DAG.
Хранилище и загрузки по дням Airflow автоматически не меняет.

Airflow 3.3.2 запущен через LocalExecutor: API/UI, scheduler и dag-processor.
Celery, Redis и triggerer для этого DAG не нужны. В существующем PostgreSQL создаются
отдельная база `airflow` и её роль; база приложения `meta` остаётся отдельной.

## Запуск (Git Bash)

Из корня репозитория, Docker Desktop запущен, .env уже существует:

```bash
source .venv/Scripts/activate
pip install -e ".[dev,stand]"
docker compose -f compose.yaml -f compose.airflow.yaml up -d --build
docker compose -f compose.yaml -f compose.airflow.yaml ps -a
```

Ожидаем: `airflow-init` завершён с кодом 0; API, scheduler и dag-processor healthy.
Init создаёт базу Airflow, постоянные ключи и пользователя UI, применяет миграции
Airflow и приложения. Это работает и с уже существующим PostgreSQL volume.

Открыть http://localhost:8081 :

- пользователь `admin`;
- пароль по умолчанию `airflow_local_password`, настройка `AIRFLOW_ADMIN_PASSWORD` в .env;
- порт меняется через `AIRFLOW_PORT`, по умолчанию 8081.

UI доступен только на 127.0.0.1. SimpleAuthManager предназначен для локального стенда.
Пароль хранится в Docker volume, а не в исходниках приложения. Токены доступа в git не хранятся.

Проверить DAG:

```bash
docker compose -f compose.yaml -f compose.airflow.yaml exec airflow-scheduler \
  python /opt/dq-bootstrap.py dags list-import-errors
```

Ожидаем: `No data found`, ошибок импорта нет. Команды Airflow запускаются через
bootstrap, чтобы получить тот же адрес базы и ключи, что и запущенные сервисы.

## Демонстрация ручного запуска на TPC-H

1. В Git Bash выполнить `python -m dq_stand status` и взять модельное время.
2. В Airflow открыть DAG `dq_monitor_checks` и нажать Trigger.
3. В параметре `logical_now` указать время в ISO 8601, например `2025-07-23T02:00:00+00:00`.
   Использовать актуальное значение из status. При необходимости снять DAG с паузы на время запуска.
4. Открыть задачу `run_due_checks`, затем Logs. В них полный отчёт ядра.
5. В `meta.run` и `meta.check_result` посмотреть те же результаты.
6. После демонстрации поставить DAG на паузу.

Ручной Trigger выполняет все активные проверки с trigger=manual и не сдвигает cron.
При PASS/SKIP задача зелёная; при FAIL/ERROR красная, хотя все проверки уже выполнены
и результаты записаны. Автоматических retries нет: нарушение данных не исправляется
повторением той же задачи. Повторить ручной прогон можно после исправления данных.

## Автоматическое расписание

Снять DAG с паузы. Он запускается раз в минуту, catchup=False, max_active_runs=1.
По умолчанию использует реальное текущее время UTC. Параметр logical_now предназначен
только для ручного Trigger и для scheduled-запусков игнорируется.

На историческом полигоне автоматический прогон ожидаемо найдёт отсутствующую партию
за вчера относительно реального времени и устаревшие данные. Чтобы демонстрировать
автоматическую работу без такой ошибки, нужно действительно догружать актуальные партии
либо использовать справочник/отдельный тестовый датасет без batch_column.
Не нужно выдавать старые данные полигона за свежие изменением системных часов.

В SQL-клиенте базы meta можно задать расписание конкретной проверки:

```sql
UPDATE dq_check SET schedule = '0 2 * * *' WHERE name = 'orders_row_count';
```

Это ежедневный запуск в 02:00 UTC (05:00 по Москве). Другие варианты:

| schedule | Частота |
|---|---|
| NULL | каждый минутный тик |
| `*/5 * * * *` | каждые 5 минут |
| `0 * * * *` | каждый час |
| `0 2 * * *` | ежедневно в 02:00 UTC |

Cron состоит из пяти полей: минута, час, день месяца, месяц, день недели.
При заданных дне месяца и дне недели применяется стандартное OR-условие croniter.
В YAML расписание проверяется при загрузке; будущая форма UI должна вызывать тот же валидатор.
Прямой SQL обходит валидацию: неверное расписание остановит автоматический тик с ошибкой
конфигурации, без частичного выбора остальных правил.

Новая активная проверка выполняется на первом тике. При простое несколько пропущенных
интервалов объединяются в один текущий, исторический backfill не делается.
FAIL/ERROR записываются как обработанная попытка: следующая попытка будет на следующем
интервале. Повторный тик того же интервала ничего не делает и не создаёт пустой run.
Ручной прогон расписание не меняет. При смене schedule новые интервалы сравниваются
с последним сохранённым scheduled_for; проверка не переигрывает старые интервалы.

## Те же расписания без Airflow

```bash
python -m dq_monitor run --due
```

Для проверки наступивших правил на модельное время:

```bash
python -m dq_monitor run --due --now 2025-07-23T02:00
```

Здесь выбор расписаний всё равно идёт по реальным часам. `--now` меняет только
время, с которым проверки смотрят на данные. Обычный `run --now ...` обходит
расписания и запускает все активные проверки. `--check` и `--due` несовместимы.

## Что хранится в базе

```sql
SELECT r.id, r.trigger, r.logical_now, c.name, cr.status, cr.scheduled_for
FROM check_result cr
JOIN run r ON r.id = cr.run_id
JOIN dq_check c ON c.id = cr.check_id
ORDER BY cr.id DESC LIMIT 30;
```

scheduled_for — реальная UTC-дата обработанного интервала cron. У ручного прогона NULL.
logical_now — время оценки данных, в демонстрации может быть модельным.
Уникальность `(check_id, scheduled_for)` защищает интервалы от повторной записи.

## Защита от одновременных прогонов

Все прогоны используют PostgreSQL advisory lock в одной базе meta. Второй CLI-прогон
получит понятную ошибку, задача Airflow — SKIPPED. Блокировка держится на том же
соединении, через которое фиксируются метаданные. При потере backend дальнейшая
запись результатов прекращается, при завершении процесса блокировка освобождается сервером.
Результат и инцидент каждой проверки сохраняются вместе, как в предыдущих этапах.

## Маршрутизация внутри Docker

На Windows запись подключения `tpch_warehouse` использует localhost:5433.
В контейнере тот же PostgreSQL доступен как postgres:5432. Compose задаёт
`DQ_CONNECTION_OVERRIDES` для этого имени подключения, не изменяя строки в meta.
Это маршрут к тому же источнику, а не способ подменить датасет. Другие подключения
без override используют собственный host/port из метаданных.

## Остановка

В UI сначала поставить DAG на паузу. Затем, чтобы освободить память:

```bash
docker compose -f compose.yaml -f compose.airflow.yaml stop \
  airflow-api airflow-scheduler airflow-dag-processor
```

PostgreSQL останется работать, история и логи сохранятся в volumes.
Для повторного запуска используется тот же `up -d --build`.
Изменения Python-кода/DAG требуют пересборки образа; изменения проверок в meta — нет.

## Порядок разбора кода

1. `scheduling.py`: валидация cron, определение интервала, выбор наступивших проверок.
2. `coordination.py`: общая блокировка всех прогонов.
3. `runner.py`: обёртка с блокировкой и сохранение scheduled_for.
4. `dags/dq_monitor_checks.py`: тонкая обёртка, вызов ядра, статус задачи и отчёт.
5. `compose.airflow.yaml`, `docker/airflow/bootstrap.py`, Dockerfile: окружение, базы и ключи.

Основание конфигурации: [Docker Compose Airflow 3.3.2](https://airflow.apache.org/docs/apache-airflow/3.3.2/howto/docker-compose/index.html),
[SimpleAuthManager](https://airflow.apache.org/docs/apache-airflow/3.3.2/core-concepts/auth-manager/simple/index.html).
