# Аномалии: запуск и разбор этапа 4

## Что добавлено

Правило `row_count` сравнивает объём с заданным диапазоном, например 450–800 строк.
Проверка `anomaly` измеряет объём и сама вычисляет диапазон из предыдущих наблюдений.
Восьмой тип поддерживает `row_count`, `null_ratio` и `mean`.

```yaml
connection: tpch_warehouse
checks:
  - name: orders_price_mean_anomaly
    dataset: dwh.orders
    type: anomaly
    params:
      metric: mean
      column: o_totalprice
      window: 30
      threshold: 3
      # min_history по умолчанию равен window; можно задать от 2 до window
```

`scope: batch` проверяет ожидаемую партию, `scope: table` всю таблицу.
Для справочников без batch_column измеряется вся таблица. Единица истории в обоих
случаях — день UTC. Внутридневные сезонные ряды этим вариантом детектора не моделируются.

## Команды

В Git Bash из корня проекта:

```bash
source .venv/Scripts/activate
docker compose up -d
alembic upgrade head
python -m dq_stand register
python -m dq_monitor checks load checks/tpch.yaml
python -m dq_monitor checks load checks/tpch-anomalies.yaml
python -m dq_monitor checks list
python -m dq_stand cycle --days 31
```

Полигон должен быть создан ранее (`dq_stand init`). Не нужно сбрасывать имеющийся полигон:
история новых проверок начнёт накапливаться со следующего дня. Старые 22 правила работают
независимо. Старые результаты другого check_id не служат историей новой проверки.
На прогретом полигоне ожидается 26 результатов, но статистические тревоги на чистых данных
возможны и требуют рассмотрения: порог 3 не гарантирует нулевую частоту ложных тревог.

## Формула и случаи без оценки

Для предыдущих значений x1…xn вычисляются среднее μ и выборочное стандартное отклонение s
(делитель n−1). Текущее значение x сравнивается с ними:

```text
z = (x − μ) / s
норма: [μ − threshold × s; μ + threshold × s]
FAIL, если |z| > threshold; точное равенство порогу проходит
```

Пример: история 9, 10, 11 даёт μ=10, s=1, при пороге 3 диапазон [7, 13].
Текущее 13 проходит, 14 проваливается. Текущая точка в расчёт своей нормы не входит.

- Нет достаточной истории: `SKIP`, но измеренное значение сохраняется для разогрева.
- Нет строк: row_count измеряет 0; null_ratio и mean дают `SKIP` без значения.
- Все значения столбца NULL: mean даёт `SKIP`, null_ratio измеряет 1.
- История постоянна: равное ей значение проходит; любое изменение даёт `FAIL`.
  z при таком изменении не определён, поэтому хранится NULL и флаг constant_shift.
- NaN, бесконечность и переполнение вычислений дают `ERROR`, а не ложный PASS.
- Ни `SKIP`, ни `ERROR` не открывают и не закрывают инцидент.
- Код выхода остаётся 0, если есть только PASS/SKIP; число skip явно видно в отчёте.

## Как выбирается история

`window: 30` означает предыдущие 30 календарных дней UTC, без текущего дня.
В каждом дне берётся последняя записанная попытка той же версии проверки.
Из неё используется конечное число со статусом PASS, FAIL или числовым SKIP разогрева.
Последняя попытка ERROR/SKIP без значения исключает день: старое успешное значение
того же дня не подставляется. Значения из более давних дней не заполняют пропуски окна.
Поэтому после пропусков/перерыва может понадобиться повторный разогрев.

Версия — SHA-256 от нормализованных параметров, типа и идентичности источника.
Имя, описание и severity в неё не входят. Параметры окна/порога входят: после изменения
конфигурации начинается отдельная история; при возврате прежней конфигурации её недавняя
история снова доступна. Старые результаты без версии автоматически не переиспользуются.

## Порядок чтения кода

1. `anomalies/detector.py`: чистая математика, вход — число и история, выход — Detection.
2. `checks/anomaly.py`: модель параметров, SQL измерения и превращение Detection в Outcome.
3. `anomalies/history.py`: fingerprint и SQL выбора истории.
4. `runner.py`: загрузка истории в CheckContext, запись результата, версии и диагностики.
5. `meta/models.py`, миграция b2e4a6c8d010: новый тип, skip, config_hash, details.
6. `report.py`, `checks/tpch-anomalies.yaml`: отчёт и готовый набор для полигона.

`CheckContext.history` по умолчанию пустой; существующие семь типов его не используют.
`Check.history_limit` по умолчанию 0, а AnomalyCheck возвращает window. Поэтому runner
запрашивает историю только для проверок, которым она нужна.
`Outcome.details` содержит диагностику, которая сохраняется в JSONB результата.

## Что хранится в meta

```sql
SELECT r.logical_now, c.name, cr.status, cr.observed_value,
       cr.expected_low, cr.expected_high, cr.details, cr.config_hash
FROM check_result cr
JOIN run r ON r.id = cr.run_id
JOIN dq_check c ON c.id = cr.check_id
WHERE c.check_type = 'anomaly'
ORDER BY cr.id DESC LIMIT 20;
```

В observed_value хранится исходная метрика. Среднее, стандартное отклонение, z,
число точек и причина пропуска находятся в details. Это даёт материал для графиков в UI.

## Миграция и откат

`alembic upgrade head` сохраняет историю этапа 3. У старых результатов config_hash=NULL,
details={}. При downgrade на старую схему наличие anomaly-проверок или skip-результатов
вызовет понятную ошибку, всё откатится транзакционно. Миграция не удаляет историю молча;
для отката базы с такими данными требуется отдельное решение о её сохранении/удалении.

## Основание и ограничения

В разделе 3.4 [Schelter et al., 2018](https://www.vldb.org/pvldb/vol11/p1781-schelter.pdf)
OnlineNormal описан через текущее среднее/дисперсию и порог стандартных отклонений.
Здесь реализован собственный вариант z-оценки со скользящим календарным окном и выборочным s;
точная идентичность реализации OnlineNormal не заявляется.

Метод не учитывает сезонность и тренд; длительная порча может сместить норму, потому что
FAIL тоже входит в историю. Нормальность распределения метрик не гарантируется.
Решения для окна/порога фиксируются до итогового эксперимента этапа 8.
